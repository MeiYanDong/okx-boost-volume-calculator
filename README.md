# OKX Boost 钱包工作台

面向 OKX Boost 活动参与者的多钱包数据工作台：把滚动快照、多链交易、活动规则和历史归档，转成可以直接行动的答案。

它回答的不是“我今天刷了几笔”，而是：

- 哪些钱包已经达到目标？
- 哪些钱包还差多少？
- 今天的结果是已确认数据，还是仍会变化的实时预估？
- 未来几次快照会不会因为旧交易到期而跌破目标线？
- 当前结果来自什么数据源，是否存在缺失或降级？

> **核心产品判断：** 链上数据只有被放进明确的时间窗口、规则版本和可靠性边界里，才能成为决策依据。

## 为什么不是一个单钱包计算器

OKX Boost 的困难不在加法，而在口径。

一个参与者可能同时维护多个钱包。每个钱包都有自己的交易历史、目标线和额外加成；统计窗口按 UTC 日滚动，旧交易会逐日到期；同一代币在不同日期还可能采用不同规则。

如果只看钱包页面或区块浏览器，用户需要手工完成：

1. 找出统计窗口内的交易。
2. 判断交易是否经过 OKX DEX Router。
3. 识别交易发生在哪条链。
4. 按交易时间应用正确的基础倍数和额外加成。
5. 汇总多个钱包，再估算未来快照的缺口。
6. 区分“没有交易”和“数据源没有成功返回交易”。

钱包一多，手工统计不仅慢，还容易把数据缺失误认为已经达标。

因此，我把产品从“输入一个地址得到一个数字”改成了一个钱包运营工作台：第一屏展示所有钱包的进度、缺口和风险，代币规则与交易明细放到二级页面处理。

## 用户真正完成的工作流

1. 导入一个或多个钱包，并设置易识别的名称。
2. 选择快照日期和单钱包目标线。
3. 刷新所有钱包，优先复用已有归档，只扫描新增区块。
4. 查看 10 日累计、10 日平均、今日数据和目标缺口。
5. 在钱包详情中核对数据源、警告、交易明细和代币加成。
6. 查看未来快照风险，必要时调整后续行动。
7. 保存归档，并通过每日自动刷新、飞书提醒或多维表格继续跟踪。

页面隐藏 Ankr、RPC、Explorer 和缓存等技术配置。用户操作的是钱包、日期、目标和规则，而不是底层数据供应商。

## 一次计算如何形成

```mermaid
flowchart LR
    A["钱包 + 快照日 + 目标线"] --> B["恢复本地 / Supabase 归档"]
    B --> C["确定最近 10 个 UTC 日期"]
    C --> D["索引发现候选交易"]
    D --> E["RPC 解析交易与 Receipt"]
    E --> F["按交易时间应用规则版本"]
    F --> G["汇总成交额、Boost 与磨损"]
    G --> H["计算达标缺口与未来快照风险"]
    H --> I["工作台 / 归档 / 飞书"]
```

系统把计算拆成五层：

| 层级 | 解决的问题 | 主要实现 |
| --- | --- | --- |
| 时间窗口 | 快照日包含当天，向前取 10 个 UTC 日期 | [`src/lib/calculator.ts`](src/lib/calculator.ts) |
| 交易发现 | 按钱包找到可能属于 OKX Router 的交易 hash | [`src/lib/ankr.ts`](src/lib/ankr.ts)、[`src/lib/explorer.ts`](src/lib/explorer.ts) |
| 交易解析 | 读取交易、Receipt、Transfer 与代币信息 | [`src/lib/parser.ts`](src/lib/parser.ts)、[`src/lib/rpc.ts`](src/lib/rpc.ts) |
| 规则计算 | 处理基础倍数、日期规则、额外加成和成交额 | [`src/lib/boostRules.ts`](src/lib/boostRules.ts)、[`src/lib/calculator.ts`](src/lib/calculator.ts) |
| 运营闭环 | 归档、增量刷新、预警、账号隔离与飞书同步 | [`server/`](server/)、[`src/App.tsx`](src/App.tsx) |

## 四个关键数据判断

### 1. 快照窗口必须成为唯一时间口径

选择 `2026-05-07` 时，统计的是包含 `2026-05-07` 在内的最近 10 个 UTC 日期。如果快照日尚未结束，结果只能写成实时预估，因为当天后续交易仍会改变结果。

页面刷新后默认回到当前 UTC 日，不允许历史归档日期悄悄覆盖当前快照口径。

### 2. 交易发现和交易解析必须分开

标准 RPC 适合读取交易、Receipt 和区块，但不一定适合在 10 日窗口中按钱包发现全部交易。系统因此把“先找到 hash”和“再解析交易”拆开：

- X Layer 当前优先使用 OKX 官方地址交易索引。
- Ankr 作为钱包索引备选。
- 标准 RPC 负责区块定位和交易解析，并在允许的小范围内兜底。
- 数据来源和降级警告必须展示给用户。

数据源失败不能被翻译成“该钱包没有交易”。

### 3. 活动规则必须按交易时间版本化

旧交易继续使用当时有效的规则，新交易采用新规则。代码更新不能让整个历史窗口突然按最新规则重算。

额外加成也不是全局开关，而是绑定：

```text
钱包地址 + UTC 日期 + 代币地址
```

这样才能处理同一代币跨日期变更、不同钱包参与时间不同等情况。

### 4. 归档是可复用数据，不是可以随意清空的缓存

日常刷新只扫描新区块；强制重扫才重建完整窗口。即使旧归档的 `windowEnd` 与当前快照日不同，也应该先恢复原始交易，再由展示层按当前窗口重新聚合。

这项判断降低了 RPC 消耗，也避免页面因日期变化把已有结果误判成“待重扫”。

## 真实故障如何改变系统

### 限流曾让半成品覆盖完整归档

全局刷新早期会并发处理多个钱包，同时并发扫描 BNB Chain 与 X Layer。短时间内的大量请求触发 Ankr 限流后，X Layer 可能失败，而 BNB Chain 仍然成功。

旧逻辑把“至少一条链成功”视为可以保存，最终用 BSC-only 半成品覆盖了原本完整的 BSC + X Layer 归档。

这次故障推动了四项改变：

1. 钱包批量刷新改为有限或串行执行，降低瞬时上游压力。
2. 索引请求增加退避重试和备选数据源。
3. 任一启用链失败时，整次多链计算失败并保留原归档。
4. 写入前检查链覆盖、区块高度和交易明细是否退化。

历史验收记录显示，2026-05-13 对 8 个钱包执行真实全局刷新时，最终 `8` 个成功、`0` 个失败，且没有再用单链半成品覆盖多链结果。该记录证明的是当时指定范围的修复结果，不代表当前生产环境永远不会失败。

详细复盘见 [全局刷新一致性修复](docs/plans/2026-05-13-global-refresh-consistency.md)。

### 日期展示曾把有效归档隐藏成空数据

另一次回归发生在滚动窗口展示：为了避免详情页显示旧日期，代码在归档 `windowEnd` 不等于当前快照日时直接清空结果，导致用户登录后看到所有钱包都需要重扫。

修复后，数据恢复与页面聚合被彻底分开：归档负责保存事实，当前快照日只决定如何展示。详见 [归档窗口复用修复](docs/plans/2026-05-31-archive-window-reuse-fix.md)。

## 从计算器到私人运营系统

项目的迭代不是简单增加页面，而是逐步补齐一条可持续运行的数据闭环：

1. **单钱包计算。** 先验证 10 日窗口、交易解析和 Boost 口径。
2. **多钱包工作台。** 把达标判断、缺口和每日数据放到同一视图。
3. **归档与增量刷新。** 避免每次重复扫描完整窗口。
4. **多链与规则版本。** 接入 BNB Chain、X Layer 和按时间生效的活动规则。
5. **可靠性加固。** 处理限流、部分链失败、交易明细缺失和归档回退。
6. **私人多用户运行。** 增加邀请制账号、工作区隔离、钱包额度和管理员权限。
7. **自动化跟踪。** 每日 Cron 增量刷新，预测未来快照，并按账号发送飞书提醒。

当前本地工作树又加入了三项运行边界：

- **活动链收敛：** 生产配置默认只刷新 X Layer；BNB Chain 代码和历史归档继续保留，但日常不请求 BSC RPC。需要恢复时，同时设置 `ACTIVE_CHAINS=bsc,xlayer` 与 `VITE_ACTIVE_CHAINS=bsc,xlayer`。
- **成本闸门：** `RPC_USAGE_PAUSED=true` 时停止 RPC、Ankr 和 Explorer 上游请求；`ADMIN_ONLY_USAGE=true` 时只允许 active admin 扫描与刷新。
- **飞书多维表格同步：** 保存归档或每日刷新后，可按“日期 + 账户 + 代币”同步成交额、磨损、倍数、加成与服务费等存储字段。同步范围受 workspace 与账号白名单约束。

这些能力在当前源码和本地测试中存在。本轮只回读了生产暂停态：主页 200、Cron 返回 paused、RPC 返回 503；没有恢复扫描或验证真实数据同步，因此不把它们描述成已经持续稳定运行的线上结果。

| 当前代码支持归档同步飞书多维表格 | 同步模块、API、6 项映射/隔离测试和 2 项写入顺序测试 | 当前分支 / 本地与 CI | 未取得本轮生产写入回执 |
| 合并前质量门禁已生效 | GitHub Actions `Quality / quality` 与 `main` 分支保护 | GitHub readback | PR #1 尚未合并，生产未部署此提交 |

当前版本还有明确边界：

- 内部结果根据链上稳定币侧成交额和活动规则估算，可能与 OKX 官方历史价格或内部口径存在差异。
- 当前活动链默认是 X Layer；Base、Arbitrum、Solana 等链不在统计范围内。
- 私人部署面向本人或少数可信用户，不适合无访问保护地公开传播。
- 本轮没有读取真实钱包归档或飞书表格；生产 API 只做暂停态 smoke，因此不展示当前用户规模、实时交易量或线上同步成功率。
